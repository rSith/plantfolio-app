# Decisions made during the overnight build

Ranshitha asked me to work without stopping for questions and to choose the simplest sensible option, writing each
choice here. Each entry: the question, what I chose, and why. Change any of them by telling me.

| # | Question | Choice | Why |
|---|---|---|---|
| D1 | Where do the tracking files go? | `PROGRESS.md`, `DECISIONS.md`, `REVIEW.md` at the repo root (moved to `docs/` in the release cleanup, 12 Nov 2026) | Asked for by name; files (not folders) at the root follow the "no new top-level folders" rule |
| D2 | May tests change the demo data? | No. Write tests use throwaway members (`test.*` usernames) that the tests create and delete. `seed.sql` is never run, because it empties every table | "Don't delete my existing data" (your account `rsith99` is in the database) |
| D3 | Obsidian notes during the night? | One summary note at the end instead of a work-log entry per step | Notes are for you to study; writing them per step would halve the work done tonight. REVIEW.md lists everything they will need |
| D4 | Collection rename and privacy change (CORE-13) | Not built | My Garden has no button or form for them; building them means designing new UI, which is your call. Create, add plants and delete are wired |
| D5 | GD (PHP's image library) is switched off in php.ini, so uploads cannot be resized | Uploads are still checked fully (finfo type, 5 MB, readable dimensions, at most 40 megapixels) and saved under random names; the resize to 1600 px runs by itself once GD is on (`extension_loaded('gd')`). I did not edit php.ini | php.ini is your machine's configuration and needs an Apache restart. To switch GD on: in `C:/xampp/php/php.ini` remove the `;` before `extension=gd` (line 931), then restart Apache in XAMPP |
| D6 | Where uploaded photos go | `public/uploads/avatars/`, `plants/`, `stories/`, `listings/`, made on first use; the database stores e.g. `plants/<32 hex>.jpg`. `photo_url()` sends `mock/…` paths to `assets/img/`, so the demo rows keep their drawings | One folder per kind keeps clean-up simple; a random name cannot be guessed or chosen |
| D8 | Changing a plant's health on the Edit page | Saved, and it adds a Story note "Health changed to Thriving on the Edit page." | `plants.health_status` is defined as the status of the newest Story entry with one (data dictionary); without the entry the two would disagree |
| D9 | Several plants added at once ("How many?") share one uploaded photo | One file, used by every row; files are deleted only when nothing uses them any more (`forget_photo()` counts uses across plants, photos, story entries, listings and avatars) | Copying the file 20 times wastes space; counting uses also covers a plant's photo that is still in its first Story entry |
| D10 | A plant saved with no photo | The species' sample drawing if the species is known, else a new neutral `assets/img/no-photo.svg` (`photo_url(null)`) | `plants.photo` may be NULL, and an empty `src` would show a broken image |
| D11 | How the Add to story and Add photo popups save | As normal form posts: plant.js checks and previews, then lets the form submit; the server saves and redirects with a toast (Post/Redirect/Get). Not fetch() | One code path, works without JavaScript, and nothing on the page can disagree with the database. The planned no-reload version can be added later on top |
| D12 | A Story entry dated before today | Saved at 12:00 that day; today's entries get the current time. Future dates become today. A care entry (Watered …) never has a health status | Entries must sort inside their day; a Story records what has happened; data-dictionary rule "care says nothing about health" |
| D13 | What Undo takes back | The action whose toast is on screen: the page that shows a toast arms Undo for it (as in stage F). Undo restores the exact row it replaced, or removes a new one, and removes Mark done's Story line | Only the session knows what to undo, so a form can never point Undo at another member's reminder |
| D14 | What the Landing page shows | Live public data: the plant with the soonest reminder, the most liked plant, and the newest AI result of each kind that is 60% or more on a public plant; a piece with no data is left out | Visitors must never see private data, and a result below 60% is "never shown as an answer" (design rule). Before, the collage read the logged-in member's arrays, which are empty for a visitor |
| D15 | Settings switches that did nothing | "Show care tasks on Dashboard" now hides Today's care (with a link back to Settings); "New plants are public" now sets the Add plant default | A saved setting that changes nothing would be a bug in the viva demo |
| D16 | When does a new interest count as "seen"? | When the owner opens that listing's interest table on My Exchanges; that view still shows "New", the next one "Seen" | Wireframe p20 UX notes ("stage B marks rows seen when the owner opens them"); showing them as Seen on the very view where they are first read would hide them |
| D17 | Where contact details are read | Only in `listing_contact()`, whose SQL returns a row only for the owner or a member with a live interest in the open listing, with unshared fields NULL. No page-wide contacts array | The privacy rule: contact details appear only after "I'm interested", and only the fields the owner chose |
| D18 | Rating rules | Enforced in the INSERT itself: the listing is closed, the rater is its owner or the one it went to, the rated member is the other side (never sent by the form), once per member (UNIQUE key) | A hand-made request cannot rate a stranger or rate twice |
| D19 | Who may start a care guide, and for what | Anyone who can see the plant (visitor on a public plant, or the owner), with the page's CSRF token; the species is read from that plant in the database, never from the request | The cache means each species is written once; reading the species server-side stops the endpoint being used to make the LLM write anything else |
| D20 | `llama3.2` is not installed in Ollama | Code and config keep `llama3.2` (as CLAUDE.md says) via `config('llm_model')`; until it is there the card shows "The care guide can't be written right now". I did not download the model | Downloading needs your OK. Fix: `ollama pull llama3.2`, or add `'llm_model' => 'llama3:latest'` to config/config.php (tested: 68 s per guide) |
| D21 | Regenerate | An owner-only POST that deletes the saved guide for that species, so the page writes a new one | One guide per species: it is shared by everyone with that species, so only an owner of such a plant may replace it |
| D22 | ML pages before the Flask service exists | The PHP side is complete and tested against a stand-in service; with Flask off the pages show their "couldn't reach" state with the member's own photo. The ?analysing and ?offline previews without a photo still show the stage F sample | The site must never break because of ML; the real service only has to answer the documented JSON |
| D23 | A Health Check result saved to the Story | A `health_check` entry: status from `disease_guides.status` (a "healthy" class without a guide gives thriving, any other needs attention), source ml, linked to the prediction; the result is attached to the plant. Not-sure results (< 60%) cannot be saved | Matches the seed's Tommy entry and the rule "below 60% is never shown as an answer" |
| D24 | Apache served the whole repository (.git, seed.sql, notes) | A root `.htaccess` (a file, not a new folder): the project folder redirects to `public/`, anything else outside `public/` is 404 | CLAUDE.md says only `public/` should be served; on XAMPP the repo sits inside htdocs. On a real host, point the web root at `public/` |
| D25 | Security headers and error display | X-Frame-Options DENY, nosniff, Referrer-Policy on every response (helpers.php); errors hidden and logged unless `app_env` is `development` | Clickjacking and type-sniffing defences cost nothing; showing errors leaks paths and code. | D7 | A second lock on the uploads folder | `public/uploads/.htaccess`: PHP switched off, script-like file names refused, no folder listing.
